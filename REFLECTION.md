Question 1 - Defend your research decision. Why did you choose your API provider? Identify an alternative you considered and the evidence from official sources that supported your choice.

If possible, I knew that I wanted to build an app revolving around creating a Pokemon team or saving Pokemon cards to a collection, as this is a topic I am interested in and understand well that would also fit the requirements for this project. I was pleased to find out that there are several APIs that would allow me to build an app of this nature. 

There were 2 APIs in particular that met the requirements for this project and allowed free access. I chose to go with TCGdex because the docs explained that it had a real server-side search ability, no API key, most cards had their real images included, and card details were included. After reading the API docs, I also determined that the REST API is the main way of obtaining the Pokemon TCG information searched and always returns predictable objects, which lines up with the Django conventions we have covered in this course. Furthermore, I liked what this API would allow me to do. I could manage a collection of cards, track their prices, and see the total value of the cards I own all at once. I thought this would fit the scope of the project best as it would model the most data that a real user would want to see.

The alternative API that I considered using was PokeAPI, which fit most of our project requirements as well. It required no signup, API key, or rate limit, and it came complete with official images that would have made my application look great. However, it had a major downfall -- this API had no text search endpoint. According to the docs, it only allowed limit and offset parameters, so I would have had to fetch the whole list and store it in a cache and then update it each day, which I did not think was the best option when I was researching which API to use. However, my current application actually does run on quite a bit of cached data, and it actually has a much larger list of Pokemon to search, so in hindsight, I don't think this API would have been a bad option as the smaller list would have been easier to cache. 

Question 2 - Explain one prototype decision. What design question did your prototype address and why? Describe the alternatives you explored, the decision you made after using it, and where that decision appears in your completed application.

I had to choose whether cards in the collection and wishlist should live in the same model or two separate models. I also have to choose whether or not a card could be listed in both at the same time (would adding a card to your collection automatically remove it from the wishlist, and could you add a card that is already in your collection to your wishlist). I asked the agent to prototype the logic for this question so I could find out what would be most user friendly. Before looking at the logic, I agreed with the agent's recommendation to have a card in the collection and wishlist live in the same model, and the card could only be added to one or the other (adding to collection would automatically remove it from the wishlist). However, after exploring the prototype, I determined that cards should be allowed to be added to both the collection and the wishlist simultaneously and shouold also have a quantity. This is more reflective of a real-life scenario. Someone may have one card, but still want another copy.

I had Claude change that because internet being out is a problem on the user end, not on the API.
